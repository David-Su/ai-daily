## REMOVED Requirements

### Requirement: 可选的同接口兜底模型

**Reason**: 兜底改为独立端点，不再与三档主模型共用服务地址和凭据。

**Migration**: 将字符串 `llm.fallback` 改为同时声明 `model`、`baseUrl`、`apiKeyName` 的对象。见「可选的独立兜底端点」。

### Requirement: 兜底不跨档也不换供应商

**Reason**: 「不换供应商」作废。不跨档仍然有效，单独保留。

**Migration**: 见「兜底不跨档」。

## ADDED Requirements

### Requirement: 可选的独立兜底端点

系统 SHALL 允许在 LLM 配置中声明一个可选的兜底端点。该项 MUST 包含型号、服务地址、API Key 环境变量名三项；三项 MUST 均非空且去除首尾空白后仍有内容。系统 SHALL NOT 从主接口继承缺省的地址或凭据。

未声明该项时，系统 MUST 按未配置兜底时的现有行为完成配置加载与调用。以字符串或其他非对象形态声明该项时，系统 MUST 视为配置无效。对象中缺任一项、或任一项为空白，系统 MUST 视为配置无效。

兜底端点 MUST 独立于三档映射：系统 SHALL NOT 要求把它写进档位字典，也 SHALL NOT 把它当成第四档。

#### Scenario: 未声明兜底时配置仍合法

- **WHEN** 配置只声明了三档主模型、未声明兜底端点
- **THEN** 系统正常完成配置加载，运行行为与未引入兜底时一致

#### Scenario: 声明完整兜底端点时配置通过

- **WHEN** 配置在三档之外声明了含型号、服务地址、API Key 环境变量名的兜底端点，且三项均非空
- **THEN** 系统正常完成配置加载

#### Scenario: 字符串形态被拒绝

- **WHEN** 配置把兜底声明为字符串而非对象
- **THEN** 系统在启动阶段报告配置校验失败，进程退出

#### Scenario: 缺项或空白被拒绝

- **WHEN** 配置声明了兜底对象，但缺少型号、服务地址或 API Key 环境变量名，或其中任一项为空字符串或仅含空白
- **THEN** 系统在启动阶段报告配置校验失败，进程退出

### Requirement: 兜底不跨档

系统 SHALL NOT 在主模型失败后改用其他档位的主模型完成该次调用。兜底 MUST 使用已声明兜底端点的型号、服务地址与 API Key，SHALL NOT 改打另一档的主模型名。

业务调用点 MUST 仍只声明档位，SHALL NOT 为了启用兜底而改写评分、即时快讯或定时汇总的调用方式。

#### Scenario: 中档失败不会改打低档

- **WHEN** 一次使用 `medium` 档的调用在主模型失败后进入兜底
- **THEN** 兜底请求携带的是兜底端点的型号，SHALL NOT 携带 `low` 档的主模型名

#### Scenario: 兜底请求走声明的独立端点

- **WHEN** 系统对兜底端点发起那一次请求
- **THEN** 请求使用的服务地址与 API Key 是兜底端点声明的那一套，而不是该次主模型请求的那一套

## MODIFIED Requirements

### Requirement: 运行中主模型耗尽后再打一枪

系统发起一次允许兜底的 LLM 调用时，MUST 先使用该次调用指定档位的主模型及其接口参数，并按既有重试策略在该主模型上重试。主模型请求成功时，系统 SHALL NOT 再请求兜底端点。

仅当该档主模型在既有重试策略结束后仍失败，且已声明兜底端点时，系统 SHALL 改用该兜底端点再发起恰好一次请求。系统 SHALL NOT 因为兜底型号或接口参数与当前档主模型相同而跳过这一次。这一次兜底请求 SHALL NOT 再套用主模型的重试次数。

主模型对应的 API Key 在发任何请求之前缺失时，系统 MUST 以现有缺 Key 方式失败，SHALL NOT 改打兜底端点。

即将向兜底端点发请求时，若读不到兜底端点对应的 API Key，系统 MUST 以与主模型缺 Key 相同的方式失败，SHALL NOT 发出该次 HTTP 请求。

兜底请求成功时，系统 MUST 将该次调用视为成功，并留下可观察的日志，指明档位、两边型号与两边服务地址。系统 SHALL NOT 因此次成功切换发送异常通知。

兜底请求失败时，系统 MUST 将该次调用视为失败，失败表现与未配置兜底时主模型最终失败一致。

下一次调用 MUST 再次先打该档主模型及其接口。系统 SHALL NOT 在进程内记住「主模型已挂」而跳过主模型。

#### Scenario: 主模型成功则不切兜底

- **WHEN** 一次允许兜底的调用中，指定档位的主模型在既有重试策略内返回成功
- **THEN** 该次调用成功返回，系统未向兜底端点的服务地址发请求

#### Scenario: 主模型耗尽后兜底一次成功

- **WHEN** 一次允许兜底的调用中，指定档位的主模型按既有重试策略结束后仍失败，且已声明兜底端点
- **THEN** 系统用兜底端点再请求恰好一次；该次成功后调用成功返回，并留下指明档位、两边型号与两边服务地址的日志

#### Scenario: 兜底一次失败则本次调用失败

- **WHEN** 主模型已失败且系统已对兜底端点发起那一次请求，该次请求也失败
- **THEN** 系统报告该次调用失败，SHALL NOT 再对兜底端点重试

#### Scenario: 未声明时不切

- **WHEN** 主模型按既有重试策略结束后仍失败，且未声明兜底端点
- **THEN** 系统报告该次调用失败，SHALL NOT 再发起另一次请求

#### Scenario: 与主模型相同仍打

- **WHEN** 主模型按既有重试策略结束后仍失败，且已声明的兜底端点与当前档主模型的型号或接口参数相同
- **THEN** 系统仍对兜底端点再请求恰好一次

#### Scenario: 下一次调用仍先打主模型

- **WHEN** 前一次调用已通过兜底端点成功返回，系统再次发起同档位调用
- **THEN** 本次请求首先携带的仍是该档主模型名及其服务地址

#### Scenario: 不可重试的主模型失败也会切兜底

- **WHEN** 一次允许兜底的调用中，主模型返回不可按既有策略重试的失败（例如模型不存在或鉴权失败），且已声明兜底端点
- **THEN** 系统不再对主模型重试，改用兜底端点再请求恰好一次

#### Scenario: 主模型缺 Key 不打兜底

- **WHEN** 一次允许兜底的调用在发请求前读不到主模型的 API Key，且已声明兜底端点
- **THEN** 系统以缺 Key 方式失败，SHALL NOT 向主模型或兜底端点发出 HTTP 请求

#### Scenario: 兜底缺 Key 时不发该次请求

- **WHEN** 主模型已失败，系统准备向兜底端点发请求，但读不到兜底端点的 API Key
- **THEN** 系统以与主模型缺 Key 相同的方式失败，SHALL NOT 发出该次 HTTP 请求

### Requirement: 启动探测不走兜底

系统在启动阶段探测各档可用性时，MUST 只使用该档主模型及其接口，SHALL NOT 在探测失败后改用兜底端点把该档标为可用。

任一档主模型探测失败或超时时，系统 MUST 中断启动并报告该档失败，即使已声明兜底端点。

评分、即时快讯与定时汇总的运行期调用 MUST 默认允许兜底，无需调用方额外声明。

#### Scenario: 某档主模型探测失败即使兜底可用也中断启动

- **WHEN** 启动探测中某一档主模型失败或超时，且配置中已声明兜底端点
- **THEN** 启动流程中断，错误信息包含该档位名，探测过程中未使用兜底端点的型号或服务地址

#### Scenario: 运行期业务调用默认允许兜底

- **WHEN** 系统在运行中为评分、即时快讯或定时汇总发起 LLM 调用，且主模型按既有策略失败、已声明兜底端点
- **THEN** 系统对该次调用使用兜底端点再请求恰好一次
