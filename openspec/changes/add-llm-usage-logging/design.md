## Context

动机参见 [proposal.md](proposal.md) 的 Why；行为契约参见 [spec.md](specs/llm-usage-logging/spec.md)。

`call_llm()` 内部的 `request_once()` 已统一处理主模型、兜底和启动探测。它在 HTTP 200 后解析响应 JSON，随后只返回 `choices[0].message.content`。模块已有 `compact_json()`，其他运行信息使用 `print()`。Docker 已启用 `PYTHONUNBUFFERED=1`。

本设计固定日志的字段、序列化方式和缺失值语义，使实施集中在一个接入点。

## Goals / Non-Goals

**Goals:**

- 复用统一响应路径与现有 JSON 序列化工具，以少量代码实现可直接搜索的单行日志。
- 用原始用量与真实请求模型支持模型级统计，并保留供应商扩展明细。

**Non-Goals:**

- 不建立日志文件、统计服务、价格表或 token 估算机制。
- 不增加 `stage`、请求 ID、耗时、批次元数据或配置开关；调用签名与业务调用点保持原样。
- 不采集错误响应或网络异常的用量，不调整评分、prompt、模型选择、重试和兜底。

## Decisions

### 1. 在统一响应处理处打印

在 `request_once()` 的 `await resp.json()` 之后、读取 `choices` 之前打印。`tier.value` 从外层调用读取，模型名使用本次请求传入的 `model_name`。这样既覆盖全部调用路径，也能在评分正文解析失败之前保留计量。

备选方案是各业务函数分别记录或增加 `stage` 参数；前者重复逻辑，后者扩大调用点与测试桩的改动。本次选择单点接入。

### 2. 直接序列化原始 usage

使用 `data.get("usage")` 获取值，通过 `compact_json()` 序列化，按规格输出固定前缀和三个字段。缺失字段和显式 `null` 都输出 `null`；明确返回的零值、空对象与扩展明细保持原样。序列化结果紧凑，字段内换行会被 JSON 转义。

备选方案是提取三个 token 数或归一化供应商字段；这会遗漏缓存、推理等明细，并引入额外兼容逻辑。日志只序列化 `usage`，避免将正文或完整响应打印出来。

### 3. 保持原调用契约

只增加标准输出，不修改请求 payload、返回类型或正文处理。HTTP 非 200 和 JSON 解析失败仍走已有错误路径，不增加异常捕获、重试或补偿请求。

备选方案是为每次失败也输出一条计量记录；通常拿不到真实用量，且需要新增状态字段，本次不采纳。

## Risks / Trade-offs

- [无 usage 的响应、超时与错误消耗不可见] -> 文档说明日志求和只代表可观测响应，不代表完整账单；不将未知消耗补为零。
- [评分和快讯都使用 low，启动探测也混入日志] -> 本次用于总量和请求模型分布，不能仅凭档位精确区分业务阶段。
- [供应商字段不同] -> 原样保留 `usage`；统计时由使用者依据实际供应商解释字段，不额外调用 LLM。

## Migration Plan

无需配置或数据迁移。应用代码与对应技术说明后按原部署方式更新程序；容器日志将出现新前缀。回滚时移除该单点日志即可。
