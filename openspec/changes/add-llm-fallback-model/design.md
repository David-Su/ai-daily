## Context

动机见 [proposal.md](proposal.md) - Why。需求契约见 [specs/llm-fallback-model/spec.md](specs/llm-fallback-model/spec.md)。

约束现状：

- 全部运行期 LLM 请求都走 `call_llm()`。评分、快讯、汇总只传 `tier`，模型名由 `LLMConfig.model_for(tier)` 取出。
- `llm.models` 是 `Dict[ModelTier, NonEmptyStr]`，键只允许 `low` / `medium` / `high`。未知键会被拒。
- 配置模型 `extra="forbid"`、启动后冻结。新增已知可选字段不会破坏旧配置；塞进 `models` 字典则会。
- 主模型按 `max_retries` 与 `RETRYABLE_STATUS_CODES` 重试。`404` / `401` 等不在可重试集合里，第一次失败就结束这一轮。
- `call_llm()` 的 `session.post` 没有超时。只有启动探测用 `startup_timeout_seconds` 包住整次调用。
- 既有约定「失败不跨档」写在已完成变更 `add-llm-model-tiers` 里：换档是质量决策，换同接口模型名不是。
- 启动探测 `_check_tier_available()` 也调用 `call_llm()`。若探测无条件吃兜底，配错的档会被捂住。

## Goals / Non-Goals

**Goals:**

- 把兜底收进 `call_llm()` 内部，三个业务调用点不改参数、不读配置。
- `models` 继续只表示档位到主模型的映射；`model_for(tier)` 继续只返回主模型。
- 未配置兜底时，请求次数与失败表现与现在一致。
- 启动探测继续回答「这一档的主模型活着」，而不是「这一档最终能吐字」。

**Non-Goals:**

- 不加运行期请求超时，也不改可重试状态码集合。
- 不做进程内熔断或粘滞：不记住「主模型已挂」。
- 不按档位各配一个兜底，也不引入第二套 `baseUrl` / API Key。
- 兜底成功不走 `notify_llm_errors`。
- 不为缺 Key 或 `401` 单独开豁免分支。

## Decisions

### 兜底字段放在 `llm.fallback`，不进 `models`

备选是 `models.fallback`，或每档一个备用名。

不进 `models` 的理由：那一层已经是档位枚举到模型名的字典。多一个非档位键要改类型，也会让「第四档」和「备用名」看起来同类。每档一个备用名能更细，但当前三档常配成同一个主模型，一个共用名就够，也符合「三档共用接口参数」的既有形状。

实现上：`LLMConfig.fallback: Optional[NonEmptyStr] = None`。缺省为 `None`；写了就必须是去空白后非空。与当前档主模型同名时，该次调用视为没有可用兜底，避免空转一次相同请求。

### 切换逻辑只放在 `call_llm()`，用默认开启的开关留给探测关掉

备选是抽一层「只打指定模型名」的内部请求函数，让探测与业务各自组装。

选开关的理由：业务调用点保持 `call_llm(prompt, tier)`；探测是唯一需要关兜底的调用方，显式传 `allow_fallback=False` 比再暴露一套内部 API 更小。默认 `True` 保证以后新增的运行期调用点自动带兜底，不必再记一次。

探测关兜底的理由：启动检查的契约是三档主模型都可用。`high` 现在没人用，若探测靠兜底过关，配错要等到升档才暴露。

### 主模型走完既有策略后，兜底恰好一次

备选是兜底再套一轮 `max_retries`，或只在 `404`（模型不存在）时切。

主模型沿用现有循环：可重试就退避打满，不可重试（含模型下线）立刻结束这一轮。之后若允许兜底且备用名可用，把 payload 里的 `model` 换成 `fallback`，再 `post` 一次。这一次无论什么状态码都不重试。

只打一枪的理由：兜底是续命，不是把故障期延迟再放大一倍。主模型已经付过退避；兜底再套 `max_retries` 会让单次调用在故障期拖得更长，而评分还可能三路并发。

不把触发收成「仅 404」的理由：用户要的是运行中预定模型没响应之后的备用，`429` / `5xx` 打满也属于这种失败。不可重试的失败同样切，避免「模型下线」还要空等重试——现有策略本来就不会重试 `404`。

缺 Key 发生在发请求之前，兜底到不了，行为与现在相同。`401` 不另开分支：它不可重试，会落到 fallback 那一枪；同一把钥匙救不了就按本次调用失败处理。

### 不粘滞，成功切换只打日志

备选是进程内记住主模型已挂，后续请求直接打兜底，直到重启或冷却。

不粘滞的理由：用户已选定「每次先打主模型」。长驻进程、两小时一抓，主模型恢复后应自己回来，不必再加冷却状态。

成功切换只打一行日志（档位、主模型名、兜底模型名），不发异常通知。通知路径挂在调用失败上；这次调用已经成功返回，再报警会把「续上了」说成故障。失败时仍抛现有的 `RuntimeError`，由原调用点决定是否通知。

### 与「不跨档回落」并存

档位仍是调用点的质量选择；兜底只换同接口下的模型名。`medium` 失败后请求里出现的是 `llm.fallback`，不会是 `models.low`。文档里把「不跨档」和「同接口备用名」写成两件不同的事，避免下次读代码的人把两者当成同一条禁令。

## Risks / Trade-offs

**主模型挂起时兜底轮不到** → `session.post` 没有超时，连接悬挂会卡在主模型的第一次请求上。本次明确不加超时。缓解：启动探测仍有超时，能拦住「进程起来时主模型已经挂死」的一部分；运行中悬挂要另开变更。

**故障期每次调用先付满主模型重试** → 不粘滞的直接代价。评分三路并发时更明显。缓解：兜底不再套重试；不可重试的失败会立刻切。

**兜底模型明显更弱时，快讯/汇总质量会在无通知的情况下下降** → 与当年拒绝跨档的理由同类，但触发条件更窄（主模型已经失败），且有日志。缓解：不自动发异常通知，但日志必须带两个模型名，便于事后对那一班推送。

**`401` 也会打一枪兜底** → 同一 Key 几乎救不了，多一次无效请求。缓解：不为此加特殊分支，保持「主模型失败且备用名不同就打一枪」的单一规则。

**仓库内 `config.yaml` 三档同名** → 兜底收益最大，也最容易配成和主模型一样，导致「配了等于没配」。缓解：同名视为该次无可用兜底；文档写明应配不同的模型名。

## Migration Plan

- 配置是加字段，不是改字段。未写 `llm.fallback` 的旧配置继续合法，行为不变。
- 部署时代码与文档同一次提交。需要兜底的环境再往 `config.yaml` 写一个与主模型不同的名字。
- 回滚：去掉 `fallback` 配置项并回退代码后，即回到现在的「主模型打完就失败」。
