## Context

现状参见 proposal.md - Why。补充实现相关的约束：`src/processor.py` 的 `html_to_markdown` 会保留 `![](url)` 图片标记；`src/llm.py` 在评分时取 `content[:2000]`、在 Digest/即时推送时取全文；存盘文件（`news-data/fetch-*.json`）保存的是评分后的条目。清洗必须发生在"送 LLM"那一侧，不能污染存盘与 `link` 字段（Digest 的来源考证逐字符依赖它）。

## Goals / Non-Goals

**Goals:**

- 一道清洗同时覆盖评分、Digest、即时推送三处 LLM 输入构造点。
- 存盘原始内容与 `link` 字段零变化；清洗可通过输入输出对比验证。

**Non-Goals:**

- 不做语义改写、概括或重排；不引入新的模型调用或外部依赖。
- 本次不碰 `pub_date` 缺失、V2EX 折叠、评分截断长度等相邻优化（已在探索中另行讨论）。

## Decisions

- **清洗点放在 LLM 输入构造侧，而非抓取存盘时**：备选是在 `html_to_markdown` 后直接改写 `entry["content"]`。否决理由是存盘内容会被永久改变，失去对照与回滚能力；输入侧清洗保留原始证据，符合"存盘为源、输入为视图"的现有分工。
- **规则限定为"可判定噪音"三类**：图片标记、推广签名/导购链接、多余空行压缩。备选是顺手加入关键词过滤或长度截断。否决理由是后两者会改变语义取舍，属于评分策略而非清洗，应另立变更。
- **空行压缩收敛到单空行分隔**：沿用 `processor.py` 已有的 `\n{3,}` 思路，保证 Markdown 段落结构可读，不过度压成单行文本。

## Risks / Trade-offs

- [过度清除] → 缓解：只匹配明确的图片标记语法与已知的推广签名模式；正文中的事实语句不在清除清单内，见 specs - 推广与广告残留清除。
- [某源把关键信息放在图片 alt 文本里] → 缓解：图片标记整体移除时其 alt 文字不单独保留，属已知取舍；若后续发现此类源，以源为单位加例外，而非放宽全局规则。
- [清洗前后效果不可见] → 缓解：任务中包含清洗前后字符数/条目数对比验证，以存盘样例为准。

## Migration Plan

- 无数据迁移，无配置变更。回滚即绕过清洗恢复原输入构造，存盘数据不受影响。
- 按开发规则同步更新 `docs/tech-spec.md` 中内容处理相关描述。
