## Context

动机与成本分布见 [proposal.md](proposal.md) - Why。需求契约见 [specs/llm-model-tiers/spec.md](specs/llm-model-tiers/spec.md)。

约束现状：

- 全部 LLM 调用经由单一函数发起，模型名从全局只读配置读取，调用点无从干预。配置对象在启动时加载一次后即冻结。
- 配置模型禁止未知字段，因此移除一个配置项会让保留该项的旧配置直接启动失败——这既是破坏性来源，也是明确的错误信号。
- 三类调用的上下文限流方式各不相同：评分按字符数分批后并发、汇总按 token 数裁剪条目、快讯无限流（实测最大 prompt 约 16k 字符，远低于任何窗口，确认不需要限流）。
- 启动阶段已有一次可用性探测，其返回值在调用处被丢弃。

关键约束是"档位只切换同一供应商同一系列的模型名"。这使得接口地址与凭据保持单一，档位不必携带连接信息。

## Goals / Non-Goals

**Goals:**

- 档位表达任务意图，模型名表达实现选择；改模型只动配置，改档位才动代码。
- 档位信息不扩散到限流与分批逻辑，保持这些代码对档位无感知。
- 启动时对三档的验证不使启动时间随档位数量线性增长。

**Non-Goals:**

- 不按档位配置采样参数（temperature 等）或输出长度上限。当前请求固定 `temperature: 0.3` 且不设输出上限，本次不改。
- 不做运行期档位切换、按成本预算动态选档、或调用量统计。
- 不优化汇总的输入规模。汇总正文占其输入约 78%，收紧它是与档位正交的另一件事。

## Decisions

### 档位参数必填，不设默认值

调用时必须显式给出档位。备选是给一个默认档（例如中档）让多数调用点省略参数。

选择必填的理由：档位是成本与质量的分配决策，默认值会让后续新增的调用点在无人过目的情况下继承某一档。必填使得每个调用点的档位在代码里可读，且新增调用点时必须做一次显式选择。代价是现有测试中的裸调用会失败——这正是想要的提示。

### 档位只承载模型名，接口参数与额度保持共享

备选是把地址、凭据、上下文额度一并下移到档位，让每档成为完整的 provider profile。

不这么做的理由有二。其一，档位在同一 endpoint 内切换同系列模型，下移连接信息只会产生三份重复值。其二更重要：上下文额度若绑定档位，档位就必须在构造 prompt 之前到场——分批与裁剪逻辑都要先知道额度才能切分条目，档位会从"调用参数"变成"贯穿数据准备流程的参数"。保持额度全局，档位就止步于发起请求的那一层。

### 不做失败自动降档

备选是高档失败后自动改用低档完成调用，提高成功率。

拒绝的理由：汇总与快讯的输出直接推送给用户且不可撤回。静默降档会让推送质量在用户无感知的情况下波动，而故障期恰好是最需要知道"这篇是弱模型写的"的时候。让调用按既有重试策略在原档内重试、失败即报错，符合现有的错误通知路径（生成失败会走错误通知而非静默跳过）。

### 三档并发探测，成功静默、失败带档位名

串行探测三档会让最坏启动耗时变为单档超时的三倍；并发探测则总耗时不变，代价是即使首档已失败也会打满三次探测请求——探测 prompt 极短，这个开销可以忽略。

返回值从"探测响应内容"改为无返回：现有调用处已丢弃返回值，保留它只会诱使未来的代码依赖一个没有意义的字符串。失败信息必须带档位名，否则拿到报错还需要逐档试错才能定位是哪一档配错了。

### 破坏性移除旧配置项，不留兼容分支

备选是把旧的单一模型配置当作某一档的默认值继续接受。

拒绝的理由：新旧字段并存时的优先级是纯粹的额外语义，没有对应的真实需求（配置文件在仓库内、单人维护）。禁止未知字段的配置模型会让旧配置在启动瞬间失败并指名字段，这个反馈比静默兼容更有用。

### 档位分配依据实测加权成本

评分与快讯用低档、汇总用中档，高档留空。

依据是四天真实数据的加权成本估算（输出按输入的约 5 倍计价）：汇总约 63%、评分约 22%、快讯约 15%。评分的输出是约 100 条 × 37 字符的紧凑 JSON 且仅供内部消费，降档近乎无损；快讯占比最小、输出为短文。汇总是唯一的长文输出，先取中档，若质量不足再升高档——高档因此不是空槽，而是预留的升档位，切换成本是一处调用点的档位值。

## Risks / Trade-offs

**即时快讯降档后输出契约被破坏** → 快讯是唯一直达用户且不可撤回的输出路径，其提示词要求五步内部推理与严格 Markdown 格式，且约定的无新内容标记被下游用作控制流分支。两种失败都不显眼：漏输出标记导致重复内容被推送；误输出标记导致热点被静默丢弃，日志仅有一行"无新内容"。缓解：用仓库内已有的真实热点数据（含实测规模最大的那一组）在低档实跑，验证格式完整性与标记触发，作为独立验证任务而非上线后依赖用户发现。若不达标，改回中档的成本是一处调用点的档位值。

**旧配置在部署时启动失败** → 破坏性移除是有意的，但部署时若配置未同步更新，进程会直接退出。缓解：错误信息由配置校验层给出并指名未知字段与缺失档位；配置文件与代码同在仓库内，同一次提交内一并更新。

**并发探测放大配置错误的表现** → 三档中任一档模型名写错都会阻断启动，可用性检查的失败面比原先扩大三倍。这是设计意图（未使用的高档若配错，应在启动时暴露而非在未来某次升档时才发现），代价是配置错误的阻塞性更强。

**档位与模型的对应关系只在配置中可见** → 读代码只能看到档位意图，具体模型需查配置。这是有意的抽象边界，但排查线上问题时需要同时看两处。缓解：档位命名保持与配置键一致，使两处可直接对应。
